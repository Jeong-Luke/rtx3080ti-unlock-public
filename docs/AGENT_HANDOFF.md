# Codex·Claude 공통 인계 절차

이 문서는 대화 기록이 없는 에이전트가 **새 사용자의 환경에서 적용 가능성을 판단하고, 승인된 범위만 단계별로 수행**하기 위한 절차입니다. 저장소를 읽었다는 사실이나 원 작성자의 성공 기록은 새 PC의 실행 승인이 아닙니다.

먼저 [사용자 책임 안내](DISCLAIMER.md)를 읽고 사용자에게 알립니다. 사용으로 발생하는 고장·오류·부팅 문제·데이터 손실 등 모든 문제와 수리·복구 비용은 사용자 본인 책임이며, 제작자와 기여자는 이에 대한 책임이나 보상을 부담하지 않는다는 점을 명확히 설명합니다. 이 안내는 개별 실행 승인이나 안전 점검을 대신하지 않습니다.

## 1. 먼저 구분할 것

- **확인된 관측:** README의 정확한 RTX 3080 Ti 한 장비에서 SS0 변경, SS1 보존, FLR, Windows 복귀 및 단기 행렬곱 검사가 이루어졌습니다.
- **아직 보장하지 않는 것:** 다른 PC의 호환성, 실패 후 복구, warm/cold 부팅 경로의 동등성, 장기 안정성, 모든 프로그램의 성능, 다음 부팅의 유지 여부.
- **배포 범위:** 소스·검사 코드·문서·정리된 측정 자료입니다. 서명 EFI, 키, 펌웨어와 개인별 USB 실행 설정은 없습니다.
- **권한 범위:** 파일 준비, 서명, 키 등록, USB 배치, 실제 부팅, GPU 실행은 다른 작업입니다. 하나의 승인을 다른 단계에 확장하지 않습니다.

도구가 없으면 필요한 관찰을 사용자에게 요청합니다. 다른 기기에 있는 에이전트는 원 PC의 파일·장치에 자동으로 접근할 수 없습니다. 스크린샷이나 과거 인계서만 보고 “직접 검증했다”고 말하지 않습니다.

## 2. 읽기 전용 환경 점검

먼저 사용자가 이미 이 시험을 시도했는지 확인합니다. 실행 중인지 불명확하거나 실패 후 상태라면 새 시도를 준비하지 말고 §7로 갑니다.

다음 항목을 해당 PC에서 확인합니다. 로컬 장치 식별정보는 공개 이슈에 붙이지 않습니다.

| 항목 | 판단 |
|---|---|
| GPU PCI vendor/device | `10de:2208`인지 확인 |
| Subsystem vendor/device | `10de:1535`인지 확인 |
| VRAM | `nvidia-smi`에서 정확히 12288 MiB인지 확인 |
| 대상 개수와 BDF | 정확히 한 대상만 식별하고 그 PC에서 읽은 주소 사용 |
| VBIOS / 드라이버 | 관측 구성 `94.02.71.00.83` / `617.42`와 비교; 다르면 현재 검증 범위 밖 |
| 부팅 / 보안 | x86-64 UEFI, 현재 Secure Boot 상태, 정상 Windows 부팅 경로 확인 |
| Windows ESP | 실제 Windows Boot Manager가 있는 파티션을 확인; 복수 후보를 추측하지 않음 |
| 디스플레이 / 복구 | GPU 리셋 시 표시 경로가 사라질 수 있는지, 다른 기기의 연락 수단 확인 |
| 사용자 자료 | 저장되지 않은 작업, 백업, 디스크 암호화 복구 수단의 보유 여부 확인 |

Windows 읽기 전용 조회 예:

```powershell
nvidia-smi --query-gpu=name,pci.bus_id,pci.device_id,pci.sub_device_id,memory.total,driver_version,vbios_version --format=csv
Get-CimInstance Win32_OperatingSystem | Select-Object Caption,Version,BuildNumber,LastBootUpTime
Confirm-SecureBootUEFI
Get-Partition | Where-Object GptType -eq '{c12a7328-f81f-11d2-ba4b-00a0c93ec93b}' | Select-Object DiskNumber,PartitionNumber,Guid,DriveLetter
```

일부 조회는 관리자 권한이 필요합니다. 권한 오류는 “기능 없음”이나 “안전함”을 뜻하지 않습니다. ESP 후보 목록만으로 Windows 파티션을 확정하지 않으며, 조회를 위해 자동으로 드라이브 문자를 할당하거나 파티션을 변경하지 않습니다.

불일치·모호함이 있으면 적용 준비를 중단합니다. 소스의 보드 제한이나 검사 결과를 수정해 통과시키지 않습니다. 다른 GPU/VBIOS 지원 추가는 별도의 개발·검증 범위입니다.

## 3. 소스와 로컬 산출물 준비

1. `SOURCE.json`, `firmware/NOTICE.md`, `docs/BUILD.md`를 읽습니다. 사용할 소스 revision과 로컬 변경 여부를 확인합니다.
2. 빌드 문서의 의존성과 명령으로 오프라인 검사를 수행합니다. 소스 검사나 단위 테스트를 실물 GPU 검증으로 표현하지 않습니다.
3. 조회용 `GA102-3080TI-PROBE.efi`, GPU 무변경 인계용 `GA102-3080TI-HANDOFF.efi`, 실행용 `GA102-3080TI-UNLOCK.efi`를 구분합니다. 파일 이름만 믿지 말고 빌드 입력과 SHA-256을 연결합니다.
4. 새로 빌드한 파일은 **미서명·미실행 산출물**입니다. 기존 관측 장비의 해시·성공 상태를 붙이지 않습니다.
5. `uefi/prepare_usb.py`는 `uefi/prebuilt/manifest.json`을 요구합니다. 빌드 문서에 따라 로컬에서 구성한 뒤 새 일반 폴더만 출력으로 지정합니다. 실제 USB 루트나 ESP는 출력 대상으로 쓰지 않습니다.
6. 기본 모드는 조회이며 `execute=0`입니다. `--mode unlock --execute`는 실행 가능한 파일 묶음을 만드는 명시적 선택입니다. 실행 준비 승인 전에는 사용하지 않습니다. `--ss1-full`은 이 절차의 범위 밖입니다.
7. 실행 준비 시 펌웨어는 핀된 manifest의 URL·SHA-256과 일치해야 합니다. 캐시가 없으면 준비 도구가 다운로드할 수 있습니다. 해시 불일치·누락·네트워크 오류를 다른 임의 파일로 대체하지 않습니다.

HANDOFF EFI는 `prepare_usb.py`의 `probe`/`unlock` 선택에 포함되지 않습니다. 별도로 준비한 HANDOFF가 무엇인지 검증해야 하며, 단순히 UNLOCK 파일의 이름을 바꿔서는 안 됩니다.

## 4. 서명·보안 정책과 개인별 설정

Secure Boot가 켜진 PC에서는 해당 PC의 정책이 허용하는 서명이 필요합니다. 작성자의 인증서가 새 PC에서도 신뢰된다고 가정하지 않습니다. 개인키를 공유하거나 공개 저장소에 저장하지 않습니다.

이 저장소에는 범용 인증서 등록·키 백업·서명 자동화가 없습니다. 사용할 신뢰 경로가 없으면 여기서 멈춥니다. 새 키 등록이 필요하다면 기존 PK/KEK/db/dbx 보존과 복구 가능성을 별도로 검토하고, 정확한 변경에 대한 사용자 승인을 받아야 합니다. 보안 기능 해제나 키 전체 초기화를 간편한 우회책으로 제시하지 않습니다.

서명했다면 원본·서명본 해시를 구분하고, 서명 검증과 PE 실행 섹션 보존을 확인합니다. SHA-256 일치만으로 유효한 서명이나 부팅 허용을 증명할 수 없습니다.

개인별 설정의 의미:

| 키 | 요구 사항 |
|---|---|
| `target` | 해당 PC에서 직접 확인한 BDF |
| `board_vendor`, `board_device` | 확인한 subsystem과 일치 |
| `execute` | 검토/인계 단계는 `0`; 별도 승인된 실행 준비에서만 `1` |
| `ss1_full` | `0` 유지 |
| `windows` | `1` |
| `windows_partition` | 해당 PC에서 검증한 Windows ESP GUID로 고정 |

작성자의 BDF·USB 드라이브 문자·파티션 GUID를 복사하지 않습니다. `prepare_usb.py`가 `windows_partition`을 자동 확정해 주는 것은 아닙니다. 이 절차에서는 모호한 Windows 후보를 남기지 않고 정확한 ESP를 확인합니다.

설정과 펌웨어는 **실행 EFI가 시작되는 같은 파티션**의 `ga102-3080ti/`에서 읽습니다. EFI 파일만 다른 파티션에 옮기면 동작하지 않습니다.

## 5. USB 배치와 무변경 인계 확인

실제 매체 작업 전, 사용자에게 다음을 한 번에 확인받습니다.

- 사용할 물리 USB와 파티션, 변경할 정확한 경로.
- 기존 작업 파일·누적 로그를 보존할 위치.
- 포맷, Windows ESP/BCD/BootOrder 변경을 하지 않는다는 범위.
- 조회/HANDOFF도 로그 쓰기와 실제 부팅을 수반한다는 점.

범용 자동 배치 도구는 제공하지 않습니다. 승인된 파일만 복사하고 실제 매체의 파일 해시를 확인합니다. 기존 사용자 자료를 지우거나 USB 전체를 초기화하지 않습니다.

본 실행 전에 GPU 무변경 HANDOFF로 **그 PC의** Windows 인계와 실제 화면 복귀를 별도로 확인합니다. HANDOFF 성공은 FLR 뒤 복구나 언락 성공을 보장하지 않습니다.

UNLOCK으로 교체할 때는 기존 `execute=0`을 유지한 상태에서 나머지 파일을 검증하고, 최종 실행 승인에 맞는 설정을 마지막에 반영합니다. 여러 파일 복사는 전원 손실에 대해 원자적이지 않습니다. 완료 여부가 불확실하면 부팅하지 않습니다.

배치 결과, 최종 서명본·설정·펌웨어 해시, 기존 로그 기준 상태를 로컬에 보존합니다. 공개 자료에는 USB 일련번호·파티션 GUID·인증서 개인 식별정보를 포함하지 않습니다.

## 6. 사용자가 직접 수행하는 단회 시험

다른 기기의 대화에서 최신 개인별 인계 정보를 볼 수 있게 준비합니다. 최소한 현재 단계, 시도 횟수, 정확한 대상, 최종 파일 해시, 승인 범위와 중단 절차를 전달합니다. 공개 문서 자체는 “배치 완료” 인계서가 아닙니다.

시작 직전 다음 위험을 설명하고 **이번 정확한 대상에 대한 1회 실행** 동의를 확인합니다.

> 실제 GPU 펌웨어 실행과 GPU 리셋을 수행합니다. 화면 소실, Windows 진입 실패, 강제 종료에 따른 데이터 손실이 가능하며 실패 후 복구를 보장하지 않습니다. 지정한 장비·USB로 이번 한 번의 시험을 지금 시작하는 데 동의하시나요?

- 작업을 저장하고 프로그램을 정상 종료합니다. 에이전트는 종료·재시작을 자동으로 수행하지 않습니다.
- 초기화 상태에 의존하는 실험입니다. Windows의 “다시 시작”과 완전 종료 후 부팅이 같다고 가정하지 않습니다. 기본 진입 계획은 정상적인 **완전 종료 후 전원 버튼으로 부팅**이며, 이것만으로 GPU의 cold 상태나 런타임 검사 통과가 보장되지는 않습니다.
- PC 제조사의 일회성 부팅 메뉴에서 검증한 UEFI USB 항목을 사용자가 한 번 선택합니다. 작성자의 메인보드 단축키를 모든 PC에 적용하지 않습니다. 영구 부팅 순서를 바꾸지 않습니다.
- 메뉴를 놓쳐 일반 Windows가 시작되면 그 상태를 기록합니다. 맞추려고 자동으로 재부팅을 반복하지 않습니다.
- 실행 후 Windows 바탕화면이 실제로 표시됐는지 확인합니다. `StartImage` 호출이나 GPU 리셋 로그만으로 Windows 복귀를 선언하지 않습니다.
- 결과가 불명확하면 반복하지 않습니다. 다음 단계의 로그 보존 전에는 드라이버 변경·재부팅·추가 언락을 하지 않습니다.

## 7. 실패·불명확한 상태

| 관측 | 조치 |
|---|---|
| 서명 거절 / `Security Violation` | 오류를 기록하고 중단. Secure Boot 해제·키 초기화로 우회하지 않음 |
| 실행 후 펌웨어 메뉴로 복귀 | 성공으로 간주하지 않음. USB 재선택 금지 |
| 실패 후 정지 / 검은 화면 | 다른 기기로 관찰과 경과 전달. 화면만 보고 실행 단계나 안전한 전원 차단 시점 추측 금지 |
| 정상 복귀 불가 | 강제 종료의 데이터 손실 위험을 설명하고 그 시점의 사용자 승인을 별도로 받음 |
| 승인 후 완전 종료 | PC가 완전히 꺼진 뒤 실험 USB를 분리. 별도 승인된 일반 Windows 부팅도 복구 보장은 아님 |
| USB 없이도 부팅/화면 복구 실패 | 추가 전원 반복·CMOS 초기화·VBIOS 플래시 금지. 별도 물리적 복구 판단 필요 |
| 디스크 암호화 복구 화면 | 사용자가 신뢰하는 로컬 절차 사용. 복구 비밀번호를 에이전트에게 전송하지 않음 |

Reset 버튼, 반복 USB 실행, 드라이버 교체, `Load Optimized Defaults`, Secure Boot 해제, 키 삭제, CSM/Legacy 전환, SS1 전체 변경은 승인된 복구 절차가 아닙니다. 로그 저장 성공도 별도 확인 없이 가정하지 않습니다.

## 8. 복귀 후 판정과 성능 비교

1. 새 Windows 부팅 시각과 사용자 관찰을 확인합니다.
2. USB 로그를 먼저 보존하고 실행 전 기준과 비교해 **이번 시도의 새 구간**만 판독합니다. 누적 로그의 과거 `PROBE COMPLETE`나 `HANDOFF BASELINE`을 이번 언락 증거로 쓰지 않습니다.
3. 정확한 대상, SS0 변경, SS1 보존, FLR 결과와 전체 오류 맥락을 확인합니다. 성공 문구 한 줄로 앞선 오류를 덮지 않습니다. 다음은 구분할 로그 표식이지 단독 성공 판정식이 아닙니다.

   ```text
   EXECUTE requested: exact target and board matched; SS1 policy=preserve
   PCIe FLR begin:
   PCIe FLR returned: result=0
   SS0/SS1 readback and FLR containment passed; actual Windows handoff and speedup still require measurement
   ```

4. `nvidia-smi` 응답, 실제 바탕화면과 정상 드라이버 응답을 별도로 확인합니다. 처리량 증가만으로 언락 성공을 증명하지 않습니다.
5. `docs/BENCHMARKS.md`의 동일 코드·조건으로 검사합니다. 사용자 동의하에 배경 GPU 부하를 줄이고 측정 후 창과 재생 상태를 복원합니다. GPU를 사용하는 다른 작업을 몰래 종료하지 않습니다.
6. 비교하려면 적용/미재적용 양쪽의 소프트웨어, 저부하 조건, 코드 해시와 계산 설정을 맞춥니다. 미재적용 상태를 얻기 위한 종료·USB 분리·일반 부팅도 사용자 직접 수행으로 별도 합의합니다.
